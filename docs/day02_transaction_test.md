# Day 2 — Stored Procedure 및 트랜잭션 검증

## 1. 작업 개요

Day 2에서는 Microsoft SQL Server의 Stored Procedure를 활용하여 RPG 게임의 캐릭터 조회, 아이템 조회 및 아이템 구매 기능을 구현했습니다.

특히 아이템 구매 시 발생하는 골드 차감, 인벤토리 갱신, 구매 이력 저장을 하나의 트랜잭션으로 처리하여 데이터 정합성을 보장하도록 설계했습니다.

## 2. 구현한 Stored Procedure

| 프로시저 | 기능 |
|---|---|
| `usp_GetCharacter` | 캐릭터 ID를 기준으로 캐릭터 정보 조회 |
| `usp_GetItem` | 아이템 ID를 기준으로 아이템 정보 조회 |
| `usp_PurchaseItem` | 아이템 구매 및 관련 데이터 변경 |

### 아이템 구매 처리 과정

1. 구매 수량 유효성 검증
2. 캐릭터 존재 및 보유 골드 확인
3. 아이템 가격과 판매 가능 여부 확인
4. 총 구매 금액 계산
5. 캐릭터 골드 차감
6. 인벤토리 수량 변경 또는 신규 지급
7. 구매 이력 저장
8. 트랜잭션 확정

## 3. 트랜잭션 및 오류 처리

구매 프로시저 내부에서 `BEGIN TRAN`, `COMMIT TRAN`, `ROLLBACK TRAN`을 사용했습니다.

정상적으로 모든 작업이 완료되면 `COMMIT`을 실행하고, 처리 중 오류가 발생하면 `TRY/CATCH`와 `XACT_STATE()`를 활용하여 트랜잭션을 취소하도록 구현했습니다.

또한 `UPDLOCK`, `HOLDLOCK`을 사용하여 동일 캐릭터에 대한 동시 구매 요청 시 데이터 정합성을 유지할 수 있도록 설계했습니다.

## 4. 테스트 결과

| 테스트 항목 | 검증 내용 | 결과 |
|---|---|---|
| 정상 구매 | 골드 차감, 인벤토리 증가, 구매 이력 생성 | PASS |
| 골드 부족 | 오류 발생 및 기존 데이터 유지 | PASS |
| 존재하지 않는 캐릭터 | 유효하지 않은 캐릭터의 구매 차단 | PASS |
| 잘못된 구매 수량 | 음수 구매 요청 차단 | PASS |
| 트랜잭션 중간 실패 | 의도적 오류 이후 골드 복구 | PASS |
| 실패 구매 자동 검증 | 오류 번호 및 데이터 변경 여부 확인 | PASS |

정상 구매 테스트에서는 `GoldTest`, `InventoryTest`, `PurchaseHistoryTest`가 모두 PASS로 확인되었습니다.

실패 구매 테스트에서도 예상 오류가 발생했으며, 골드, 인벤토리 및 구매 이력이 변경되지 않은 것을 확인했습니다.

트랜잭션 중간 실패는 별도의 테스트 코드로 재현하여 ROLLBACK 동작을 검증했습니다.

## 5. 학습 및 개선 사항

이번 실습을 통해 Stored Procedure의 실행 구조와 트랜잭션의 원자성(Atomicity)을 확인했습니다.

특히 구매 작업에서 여러 테이블을 변경할 경우 일부 작업만 반영되지 않도록 처리하는 것이 중요하다는 점을 학습했습니다.

향후 개선 항목은 다음과 같습니다.

- 두 세션을 이용한 동시 구매 처리 결과 검증
- 잠금 대기 및 교착 상태 분석
- 대량 데이터 환경에서의 실행 계획 확인
- 인덱스 설계 및 쿼리 성능 최적화
